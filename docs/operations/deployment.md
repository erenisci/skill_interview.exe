# Deployment

> **Purpose.** How a build reaches a user's machine, and what has to be true first.
> **Related.** [../project/release-plan.md](../project/release-plan.md) · [ci-cd.md](ci-cd.md)

"Deployment" here means **shipping a Windows installer**. There is no server, no infrastructure, and nothing to roll
back centrally — once a user has installed a version, that version is theirs until they install another.

That asymmetry is why the pre-release checks are strict: a bad release cannot be recalled, only superseded.

## Environments

|              | What it is                                          | Where data lives                                 |
| ------------ | --------------------------------------------------- | ------------------------------------------------ |
| **dev**      | `npm run dev`                                       | Project directory, or `SKILL_INTERVIEW_DATA_DIR` |
| **release**  | Packaged installer                                  | `%APPDATA%/skill-interview/skills.db`            |
| **clean VM** | A throwaway Windows VM used to verify the installer | Its own `%APPDATA%`                              |

The clean VM is the closest thing to a staging environment and it is mandatory before every release. A dev machine
has Node, Ollama, a model, and years of accumulated state — it cannot tell you whether a new user can install the app.

## Prerequisites

Before building a release:

- All CI stages green on `main` ([ci-cd.md](ci-cd.md)).
- `npm run eval` run locally, scores recorded, no regression ([../llm/eval-harness.md](../llm/eval-harness.md)).
- Migrations tested against a **copy of a real, populated database**, then the app opened against it.
- `CHANGELOG.md` promoted and `package.json` version bumped in the same commit.

On the user's side, the app requires Windows 10 or 11, Ollama installed and running, and an 8B-class model pulled.
The app checks all three at startup and routes to the setup screen rather than failing
([../product/feature-specs.md](../product/feature-specs.md)).

## Steps

1. Merge everything intended for the release into `main`.
2. Bump the version and promote the changelog entry.
3. `npm run build` — produces the Windows installer.
4. Install on a clean VM. Walk [../quality/qa-checklist.md](../quality/qa-checklist.md) end to end.
5. Install over the **previous version** on a machine with real data; confirm skills, cards, questions, and review
   history survive the migration.
6. Tag `vX.Y.Z` and push the tag.
7. CI builds the tag and attaches the installer to the GitHub release.
8. Write the release notes from the changelog. State plainly if a migration is irreversible.
9. `/acta:track` to sync the docs.

## Verification

After publishing, on a machine that has never run the app:

- [ ] The installer downloads and runs; the SmartScreen path is understood and documented if unsigned.
- [ ] With Ollama absent, the setup screen appears with correct instructions.
- [ ] After following those instructions, adding a skill produces a card.
- [ ] The daily set is reachable.
- [ ] The database is created in `%APPDATA%`, not the install directory.

And on a machine upgraded from the previous version:

- [ ] Existing data is intact and the schema version advanced exactly once.
- [ ] Content generated by the older version still renders.

## Rollback

There is none, centrally. A user's recovery path is to uninstall and install the previous release from GitHub, with
their database intact — which only works if migrations were **forward-only and additive**
([../architecture/database-design.md](../architecture/database-design.md)).

This is precisely why a migration that cannot be tolerated by the previous version is a **major** version bump and
must be called out in the release notes.
